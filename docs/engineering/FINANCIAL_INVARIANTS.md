# SplitFlow Financial Invariants

SplitFlow's safety model is based on deterministic invariants. AI can assist with interpretation and drafting, but money-critical decisions must be produced and checked by typed application logic.

## Invariants

| Invariant | What it protects | Failure example | Code or test enforcement |
| --- | --- | --- | --- |
| AI can propose but cannot finalize money. | Prevents hallucinated amounts from becoming payment truth. | An LLM says "Mina owes 12,000 KRW" without deterministic calculation. | `lib/prototype-proposals.ts` creates proposals through deterministic recalculation; `tests/unit/financial-invariants.test.ts` validates parsed proposals. |
| All final shares must be generated by deterministic code. | Keeps final amounts reproducible and testable. | A UI copies AI text into `shareAmount` without recalculating. | `calculateItemizedSplit()`, `calculateSplit()`, and invariant tests for tampered totals. |
| Sum of participant shares must equal the total after rounding. | Prevents lost or created money. | 10,000 KRW split three ways becomes 3,333 + 3,333 + 3,333 = 9,999. | `lib/domain/itemized-split-engine.ts`; `tests/unit/itemized-split-engine.test.ts`; `tests/unit/financial-invariants.test.ts`. |
| Rounding must be deterministic and auditable. | Ensures repeat runs produce the same answer and reviewers can inspect the adjustment. | Different participants receive the remainder on separate runs. | `roundingAdjustments` in `calculateItemizedSplit()` and deterministic rounding tests. |
| Participant opt-outs or claim changes must trigger recalculation or review. | Prevents stale accepted amounts from surviving changed facts. | A participant opts out of meat but everyone else's old amount remains ready. | `applyWorkflowAction()`, `recalculateProposal()`, `deriveSplitReadiness()`, and opt-out invariant tests. |
| Recalculation must trigger reconfirmation before payment readiness. | Prevents "accepted" responses from applying to changed amounts. | Alex accepts 20,000 KRW, then recalculation changes him to 24,000 KRW and the app still marks ready. | `needs_reconfirmation` workflow state and workflow repository tests. |
| A proposal with unresolved claims cannot be ready to pay. | Prevents claimed money from being treated as confirmed money. | Sarah says she paid 10,000 KRW, but the organizer never confirms it and the proposal is marked ready. | `lib/domain/financial-invariants.ts`, `deriveSplitReadiness()`, and unresolved-claim tests. |
| Conflicting claims must produce review, not readiness. | Prevents contradictory payment evidence from being silently accepted. | Sarah has two unresolved claims, one for 10,000 KRW and one for 12,000 KRW. | `findConflictingPaymentClaims()` and conflict tests. |
| Status transitions must be explicit and testable. | Makes payment readiness explainable and prevents hidden UI-only transitions. | A button directly marks a draft proposal settled. | `lib/workflow/schema.ts`, `applyWorkflowAction()`, workflow repository tests, and state-machine docs. |
| Money values should avoid floating-point ambiguity where applicable. | KRW calculations should use integer minor units. | A cost is stored as `128000.5` KRW and later rounded differently. | `lib/domain/money.ts`, `lib/domain/financial-invariants.ts`, and integer-money tests. |

## Current Invariant Module

`lib/domain/financial-invariants.ts` checks:

- Missing deterministic calculation results
- Non-integer money values
- Proposal total mismatches
- Paid-by totals that do not reconcile
- Participant fair shares that do not reconcile
- Net balances that do not sum to zero
- Calculation warnings
- Conflicting unresolved payment claims
- Readiness while claims are unresolved
- Readiness while active participants are unconfirmed

This module is intentionally small. It does not replace the existing split engines or workflow service; it gives reviewers and tests one clear place to inspect the safety rules.

## Reviewer Reading Path

1. Read `lib/domain/itemized-split-engine.ts` to see deterministic item eligibility, rounding, net balance, and settlement calculation.
2. Read `lib/readiness.ts` to see how blockers become operational readiness.
3. Read `lib/domain/financial-invariants.ts` to see the explicit safety checks.
4. Read `tests/unit/financial-invariants.test.ts` to see the messy cases converted into executable proof.
